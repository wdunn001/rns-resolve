# Security policy

## Reporting a vulnerability

Report privately, before public disclosure, through
[GitHub private security advisories](https://github.com/wdunn001/rns-resolve/security/advisories/new)
on the public mirror. Do not open a public issue for an unfixed vulnerability.

Include what you need to make the problem reproducible: the version or commit,
what you did, what you expected, and what happened. A proof of concept helps
and is welcome; do not run one against someone else's resolver.

## What counts as a vulnerability here

This is naming infrastructure, so the interesting failures are about a party
gaining authority it should not have, not only about crashes. Treat these as
security issues:

- **Trust boundary bypass.** Anything that lets a resolver's answer reach a
  client that supplied a literal destination hash, including a fallback for a
  hash that timed out.
- **Registration forgery.** Registering a name for a destination the caller
  does not own, or any path where the target comes from the request instead of
  being derived from the caller's identity.
- **Verification bypass.** A record accepted without a valid signature, with a
  public key that is not bound to its identity field, or with a target that
  does not re-derive.
- **Replication abuse.** Getting an unsigned or attested record to replicate,
  bypassing the peering stamp or the identified-link requirement, or using the
  sync payload caps to exhaust a peer.
- **Operator surface exposure.** Reaching the admin endpoints or the record
  listing from outside the loopback and proxy gates described in
  `docs/ADMIN.md`, or finding record data on the public health port.
- **Identity leakage.** Any path that writes the resolver's private identity,
  or a registrant's, into a log, a page, a health reply, or a peer message.

Denial of service against a single resolver is lower severity by design: the
system expects resolvers to disagree, fail, and be replaced by another. Report
it, but a client that cannot reach one resolver is a supported state, not a
break.

## What is out of scope

- Missing rate limits or hardening on a deployment you control that has been
  exposed contrary to the documentation, for example publishing the private
  port or the dashboard on an untrusted network.
- Reports that a resolver returned an announce-heard candidate you did not
  like. Candidates are returned with evidence and are never authoritative; that
  is the design, and `.agents/skills/trust-invariants/SKILL.md` explains why.
- Findings generated by a scanner without a demonstrated impact on this
  codebase.

## Deployment expectations

A resolver is meant to be reachable over Reticulum. Its **public health port**
carries no record data. Its **private port** is loopback only and carries the
record listing, registration, and the operator endpoints. The operator
dashboard expects to sit behind an authenticating reverse proxy and additionally
refuses any request that does not arrive from loopback or from a configured
trusted proxy carrying an authenticated user header.

If you publish the private port or the dashboard on an untrusted network, you
have given away the operator surface, and no code in this repository can take
that back.
